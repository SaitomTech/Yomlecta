# YouTubeインポート：取得時優先・必要時変換の設計

設計・2026-09-09。旧案を置き換える。実装済みの方針を記録する。

プロジェクトメタデータの正本は現在`project.json`ではなく`AppLocalData/library/library.sqlite`です。動画assetの配置とインポート処理はこの文書の説明を使い、保存commandとDB台帳は[SQLite永続化設計](./sqlite-detailed-design.md)を参照してください。

## 1. 達成する目的

公開済みの単一YouTube動画について、映像と音声を含むローカル動画を1本取得し、
WebViewで扱いやすいMP4としてプロジェクトに保存する。その同じパスを再生・画像抽出・音声抽出に渡せるようにする。

今回の成功条件は「取得した動画とプロジェクトが保存され、次回も参照できること」。
WebViewでの再生成功や全形式の解析成功はインポートの成功条件にしない。
各機能は同じファイルを処理し、処理できなければその機能のエラーを表示する。

以下は今回の目的に含めない。

- 取得した動画の無条件な再エンコード。
- 変換後も再生できない動画の修復・代替形式の再取得。
- 原本とプレビュー用動画の二重管理。
- 独自の並列ダウンロード、キャッシュ、途中再開、永続ジョブ管理。
- 取得後の縮小、必要のない音声・映像変換。

既存の遅さの主因はまだ確定していない。本設計で保証するのは、対応形式なら
追加処理を発生させず、形式調整が必要な場合も必要なトラックだけを変換することである。
ダウンロード速度や変換時間の上限は保証しない。

## 2. 正常系は一本道

URLの情報確認は、取得する動画をユーザーが確認するための既存機能として残す。

取得開始後は常に同じ手順とする。

1. 新規プロジェクトIDと保存先を用意する。
2. yt-dlpを1回実行する。映像・音声の取得と、必要な結合を任せる。
3. yt-dlpが報告した最終ファイルを確認する。
4. ffprobeでメタデータを読み、MP4・H.264・8bit `yuv420p`・AACか判定する。
5. 基準外なら必要なトラックだけをFFmpegで変換し、MP4にまとめる。基準内なら取得ファイルをそのまま使う。
6. 変換後のファイルをffprobeで確認し、プロジェクトを保存する。
7. 同じファイルをプレビューと後続の解析へ渡す。

アプリの分岐は「保存したファイルが基準形式か」と「どの要素を調整するか」の判定に集約する。
音声付き単一ファイルと映像・音声別配信の違いはyt-dlpが処理する。
形式調整時は映像・音声をコピーまたは変換し、一つのMP4に格納する。

エラーとキャンセルの処理は残す。「一本道」は正常系に形式別の経路がないという意味であり、
終了コードや保存失敗を無視するという意味ではない。

## 3. 責任分担

| 担当                   | 責任                                                               |
| ---------------------- | ------------------------------------------------------------------ |
| yt-dlp                 | 配信形式選択、取得、通信リトライ、必要な結合、内部一時ファイル管理 |
| 同梱FFmpeg             | yt-dlpの結合、必要時のMP4化・トラック変換                          |
| ffprobe                | 取得前後の長さ・解像度・FPS・コンテナ・コーデック情報の取得        |
| downloader.ts          | 1回の取得呼び出し、形式判定、必要時の変換、SelectedVideoの構築     |
| インポートの呼び出し元 | 新規プロジェクトの保存、失敗時の片付け                             |
| OS境界                 | 同梱バイナリの場所、実行中プロセスと子プロセスの停止               |
| UI                     | 状況表示、キャンセル、取得後のプレビュー                           |

汎用ワークフローエンジン、形式別Strategy、ジョブDBは作らない。
複数方式を差し替えるための抽象層も作らない。

## 4. 取得条件

H.264・AAC・MP4の組み合わせを最優先し、利用できない場合は一般的な形式へ順にフォールバックする。
フォールバックはyt-dlpの1回の形式選択式に含め、失敗後の再取得はしない。
コンテナは取得後のffprobeで判定し、必要時だけMP4へ調整する。

既存の画質入力は維持する。これは取得前のパラメータであり、取得後の処理を分岐させない。

| 入力  | 形式指定の先頭                                                      |
| ----- | ------------------------------------------------------------------- |
| 720p  | `bv[ext=mp4][vcodec^=avc1][height<=720]+ba[ext=m4a][acodec^=mp4a]`  |
| 1080p | `bv[ext=mp4][vcodec^=avc1][height<=1080]+ba[ext=m4a][acodec^=mp4a]` |
| best  | `bv[ext=mp4][vcodec^=avc1]+ba[ext=m4a][acodec^=mp4a]`               |

bvは映像専用形式、baは音声専用形式、bは音声付きの単一形式。
先頭からMP4・H.264・AACを優先し、対応する配信がなければMP4内の別音声、別音声形式、一般形式へ進む。
音声トラックは1本を対象とし、音声言語の独自選択は追加しない。
画質上限を超えた再取得や、別コーデックを指定した再実行はしない。取得後の変換はこの形式選択とは独立した1回の処理とする。

720p/1080pは上限であり、厳密な出力解像度ではない。UI表記は「720pまで」「1080pまで」。
最高画質は高さ上限なし。既定値の720pを維持し、画質選択を削除する仕様変更は混ぜない。

## 5. 実行するコマンド

概念上の引数を以下に示す。実装ではシェル文字列を組み立てず、引数配列で渡す。

```text
yt-dlp
  --ignore-config
  --no-playlist
  --no-cookies
  --no-cache-dir
  --no-simulate
  --newline
  --progress
  --progress-template download:VLN_PROGRESS:%(progress._percent)s|%(progress._speed_str)s|%(progress._eta_str)s
  --format <画質から決まる選択式>
  --ffmpeg-location <同梱FFmpegの絶対パス>
  --output <新規プロジェクト>/source/source.%(ext)s
  --print after_move:VLN_RESULT:%(filepath)j
  <正規化したYouTube URL>
```

取得・結合はこの1回の実行で終える。取得後に基準外だった場合だけ、アプリからFFmpegを1回起動する。
対応形式ならそのFFmpegは起動しない。変換時は基準外の映像・音声だけを変換し、基準内のトラックはストリームコピーする。

情報確認は別のyt-dlp呼び出しとし、同じignore-config等の実行ポリシーを使う。
タイトル確認時とダウンロード時で計2回の情報解析は許容する。
期限付き配信URLを再利用するためのキャッシュは持たない。

専用の結果接頭辞とJSON文字列として出力したfilepathを読む。
同梱版2026.08.19で上記テンプレートを実際に検証してから採用する。
一般ログの「Destination」などからパスを推測しない。
出力先のファイルをprefix検索して代用品を選ぶ処理は削除する。

## 6. 保存物と結果の扱い

```text
AppLocalData/
  library/library.sqlite
projects/<projectId>/
  source/
    source.mp4 または source.<yt-dlpが選んだ拡張子>
```

成功時に残す動画は1本。基準外の場合は一時的な`source.compatible.mp4`を作成し、
確認後に`source.mp4`へ置き換えて元の取得ファイルを削除する。変換不要なら追加ファイルを作らない。
拡張子・表示名・MediaSource.pathは最終ファイルに合わせる。

最終ファイルの扱いはすべて同じ手順とする。

- yt-dlpの終了コードが0で、結果パスが1つ報告されていることを確認する。
- パスが今回のsourceディレクトリ内の実在する通常ファイルで、サイズが正であることを確認する。
- ffprobeで読み取り、正の長さと映像の幅・高さ、音声トラックの存在を確認する。
- コンテナ、映像コーデック、ピクセル形式、音声コーデックを記録する。
- 基準外のコンテナはMP4へ、基準外の映像はH.264・`yuv420p`へ、基準外の音声はAACへ調整する。
- 取得前のタイトル等と、実ファイルから読んだメタデータでSelectedVideoを構築する。

ffprobeは全編デコード検査ではなく、Crop等に必要な数値の取得と、
基準形式の判定、明らかに不完全な結果を保存しないための確認。
実ファイルのメタデータを優先し、取得前のdurationとの厳密一致は要求しない。

MediaSourceは1本の最終ファイルのパスのまま。プレビュー専用パスや原本管理情報は追加しない。
インポート後のYouTube動画はMP4、それ以外のローカル動画は現在の拡張子型で表現する。
型・schema・ファイルピッカーの許可リストを「WebViewで再生可能な形式一覧」として使用しない。
同梱yt-dlpが既存の拡張子一覧外のコンテナを出した場合も、取得後にMP4へ調整する。

## 7. 取得成功と再生成功を分ける

プロジェクト保存が成功したら、インポートは完了する。
その後にWebViewでプレビューする。再生エラーで取得失敗に戻したり、動画を削除したりしない。

インポート画面の「次へ」は保存完了で有効にする。
canplayを取得完了の必須条件にしない。既存の再生状態はプレビュー表示にだけ使う。

変換後も再生に失敗した場合は「動画は保存されましたが、プレビューを再生できませんでした」と表示する。
再生エラーを起点にした再取得や再変換は追加しない。
Crop・Trimなど再生を必要とする操作が使えない場合もあるが、互換性対応は本設計の範囲外。
後続処理が失敗した場合は、その工程でエラーを表示し、保存した動画は保持する。

画像抽出や文字起こし用の音声抽出など、明示的な解析に必要な既存処理は継続する。
本設計が除くのはインポート時の互換変換であり、解析に必要な処理ではない。

## 8. 状態表示

インポート側の状態は idle / importing / ready / error の4つとする。
キャンセル完了はidleに戻す。永続化する状態機械は追加しない。

importingの間は工程に応じて次を表示する。

- 取得中：動画を取得しています
- 確認中：動画の形式を確認しています
- 変換中：アプリで再生できる形式に合わせています（映像・音声・MP4化の内容を表示）
- 保存中：プロジェクトを保存しています

結合・確認・保存を厳密に分けるためのログ推測やpostprocessorイベント依存を作らない。

yt-dlpのprogress-templateから得られる取得率・速度・ETAを補助表示してよい。
値は「現在取得中のファイル」の値として表示し、全工程の率にはしない。
ダウンロードが完了したら補助値を消し、確認・変換・保存は不定進捗で表示する。
ストリーム別の状態配列、容量加重の総合進捗、独自のETA計算は追加しない。
進捗行は専用接頭辞で識別し、stdout全体を無制限に蓄積しない。

## 9. キャンセル・失敗時の所有権

保存を含むインポートの呼び出し元が、今回作った新規ディレクトリの所有者になる。
取得関数は失敗を返し、ディレクトリを独自に削除しない。
ネットワークリトライはyt-dlp内部に任せ、アプリ側で呼び直さない。

中止・取得失敗・メタデータ読取失敗・保存失敗は同じ終了経路に集める。

1. 実行中のインポートプロセスと子FFmpegを停止し、終了を待つ。
2. 今回の未確定プロジェクトディレクトリを片付ける。
3. キャンセルならidle、それ以外ならerrorを表示する。

停止確認に失敗したときは書き込み中のディレクトリを削除せず、停止失敗を返す。
クリーンアップ失敗は元のエラーを隠さず記録する。
強制終了後の自動回収、再開用manifest、定期掃除は追加しない。

キャンセル要求を受け付けるのは取得・形式確認・変換まで。
プロジェクト書き込みに入る直前にキャンセルを再確認し、その後は
キャンセルボタンを無効にして保存完了または保存失敗まで処理する。
確定済みプロジェクトをキャンセルやプレビューエラーで消さない。
保存の途中で画面を離れた場合も保存結果を優先する。

yt-dlpが子FFmpegを起動するため、親だけkillして完了にはできない。
OS境界に、同梱バイナリを解決して今回のプロセスグループを起動・停止する小さな実行処理を置く。
既存ランナーで親子停止が保証できるなら再利用し、できなければRust側で実装する。
汎用のジョブスケジューラは不要。名前検索による他のFFmpegの一括停止はしない。

## 10. 変更範囲

| 箇所                        | 変更                                                   |
| --------------------------- | ------------------------------------------------------ |
| youtube/downloader.ts       | 1回取得、形式優先、ffprobe判定、必要時の形式調整に集約 |
| youtube/metadata.ts         | 共通実行ポリシーを適用                                 |
| youtube/types.ts・Import UI | 取得・確認・変換・保存の状態と、変換理由の表示を追加   |
| App.tsx・projectAssets.ts   | 片付けの責任を1箇所に集約、保存確定を管理              |
| media/ffmpeg.ts             | 必要なトラックだけを変換するMP4調整処理を追加          |
| lib/tauri・src-tauri        | 同梱FFmpegのパス解決と親子プロセス停止                 |

sourceパスは既存の動画利用箇所へそのまま渡す。
Cropや解析のロジック、プロジェクトのバージョンは、形式制限の実在が見つからない限り変更不要。
HTTPサーバーのMIMEは実拡張子に対応させるが、MIME変更で再生互換性を保証したとは扱わない。

## 11. 実装時の受け入れ条件

- H.264/AAC/MP4は追加のFFmpegなしで保存される。
- VP9/OpusやMKV等は同じインポート経路を通り、基準外の要素だけが1回調整される。
- 音声付き単一ファイルも映像・音声別配信も、1回のyt-dlp実行で動画1本を保存する。
- 変換不要なら実ファイルの拡張子・パスが、変換時は`source.mp4`がproject.jsonと表示名に正しく反映される。
- 画質上限の選択を固定形式一覧で検証し、実行するyt-dlpの版で挙動を確認する。
- 変換中は変換理由を表示し、WebViewで再生可能なMP4を保存する。
- 次回起動時にプロジェクトを開き、同じ動画パスを参照できる。
- 取得中・結合中・変換中のキャンセルで子プロセスが残らず、未確定データが片付く。
- 不正パス、結果欠落、ffprobe失敗、保存失敗を成功として扱わない。
- 開発実行と配布.appの両方で同梱FFmpegを発見できる。
- 関連テスト・型チェックを行い、H.264/AAC/MP4とH.264/Opus/MKV等で形式調整、再生、画像・音声抽出を試す。

取得全体・メタデータ読取・プロジェクト保存の経過時間を開発ログに記録する。
別の計測基盤やログ永続化は追加しない。yt-dlp内部の取得・結合の内訳は必要時だけ調査する。
