# 複数プロジェクト差分整理・堅牢化 実行計画

# 現行実装について

この計画書の保存層に関する記述は旧`project.json`方式を前提にした履歴です。現在の実装では [SQLite永続化設計](./sqlite-detailed-design.md) に置き換わっており、チェック項目やJSON保存手順を新たな実装要件として扱いません。

## 1. 目的

現在の複数プロジェクト・複数動画・複数記事対応の差分を、初回リリース前に安全で変更しやすい状態へ整える。

この計画では、次の問題をまとめて解消する。

- プロジェクト保存形式と実行時状態の二重管理
- ストレージ初期化、作成、削除におけるデータ整合性の不足
- 過去に到達したステップへ戻る機能と、再生成時の無効化ルールの不足
- 動画追加UIの入れ子操作やダイアログのアクセシビリティ問題
- `ProjectDetailPage.tsx`への責務集中
- 一時サムネイルや失敗時ファイルの残留
- 現在参照されていない互換コード、型、フィールド
- 新しい保存・遷移仕様を保護する自動テストの不足

## 2. 前提

### 2.1 既存ユーザー互換は扱わない

現時点では既存ユーザーがいないため、旧形式のプロジェクトを新形式へ移行するマイグレーションは実装しない。

- 旧形式の読み込み互換を維持しない
- 旧形式専用の型、分岐、修復処理を残さない
- 開発中の旧プロジェクトはストレージバージョン変更時に一度だけ初期化してよい
- 初期化に失敗した場合は処理を中断し、部分的に消えた状態で続行しない
- 保存ファイルのバージョンが現行と異なる場合は、暗黙に読み替えず明示的に拒否する

### 2.2 実行中のデータ整合性は保証する

旧データ互換が不要でも、現行バージョンで次の失敗は発生し得る。

- ディスク容量不足
- ファイル権限エラー
- ffmpeg処理の失敗またはキャンセル
- アプリ終了やクラッシュ
- 同じ操作の連続実行

作成・更新・削除は、これらが起きてもプロジェクトJSONと実ファイルの参照関係を壊さないようにする。

### 2.3 UIの大幅な再設計はしない

現在の画面構成とユーザー導線は維持する。今回行うのは責務分割、状態管理の整理、不具合修正、アクセシビリティ改善であり、見た目の全面刷新ではない。

## 3. 完了条件

- 現行スキーマだけを完全に検証して読み書きできる
- ストレージ初期化が一度だけ、失敗を隠さず実行される
- 作成・削除・保存の途中失敗で、参照切れしたプロジェクトを作らない
- 到達済みステップには前後どちらにも移動できる
- 上流データを変更または再生成した場合、無効になった後続ステップへは直接移動できない
- 単なる閲覧やステップ移動では、到達済み情報を失わない
- プロジェクト、動画、記事、一時ファイルの削除失敗を適切に扱える
- 動画追加UIでFinderとYouTubeの操作が同時発火しない
- すべてのダイアログに名前、フォーカス管理、Escape操作がある
- `ProjectDetailPage.tsx`が機能単位のコンポーネントとhookへ分割される
- 宣言だけ残っている関数や、読み取られないフィールドが整理される
- ストレージ、ワークフロー、主要UI操作を自動テストで保護する
- `bunx tsc -b --pretty false`、`bun run lint`、`bun run fmt:check`、`git diff --check`が通る

## 4. 設計方針

### 4.1 永続モデルと画面用ワークスペースを分ける

現在の`MediaProject`は、永続化する`videos`・`articles`に加えて、選択中記事の`source`・`slides`・`workflow`などをルートにも複製している。この構造では、保存前の同期漏れや不要なrevision更新が起きやすい。

最終形は次の責務に分ける。

```text
PersistedProject
  id / title / videos / articles / activeArticleId / timestamps

Article
  inputMedia / settings / slides / outputs / workflow

ArticleWorkspace
  projectId / articleId / project metadata / active Article
  画面と各処理が参照する実行時ビュー
```

方針:

- 正規データは`PersistedProject.articles[]`内の`Article`だけに置く
- 選択中記事の内容をプロジェクトルートへ複製しない
- 既存の解析関数が一度に移行できない場合は、純粋な`toArticleWorkspace()`アダプターを一時的に使う
- アダプターは保存責務を持たず、逆同期関数も作らない
- 記事更新は`updateArticle(project, articleId, updater)`のような明示的な関数に集約する
- `contentRevision`などを残す場合は、実際に内容が変わったときだけ増やす

### 4.2 記事資産の保存先は引数で決める

モジュールグローバルな`activeArticleContext`は廃止する。

```ts
getSlideAssetPath(projectId, articleId, slideIndex)
getAudioAssetPath(projectId, articleId)
getRawTranscriptAssetPath(projectId, articleId)
```

- すべての資産APIへ`projectId`と`articleId`を明示的に渡す
- 非同期処理が画面遷移後も続いた場合に、別記事のディレクトリへ書かない構造にする
- パス組み立ては一箇所に集約し、各IDを検証する
- `runs/current`を使い続ける場合も、記事IDを含む完全なパスを関数内で組み立てる

### 4.3 「最後に見たステップ」と「到達可能なステップ」を分ける

`lastVisitedStep`だけでは、再開位置と成果物の有効性を同時に表現できない。

最低限、次の2つを分離する。

```ts
type ArticleWorkflow = {
  lastVisitedStep: ProjectStep
  maxReachedStep: ProjectStep
  lastOpenedAt: string
}
```

- `lastVisitedStep`: 次回開いたときの表示位置
- `maxReachedStep`: 現在の成果物で移動可能な最終ステップ
- ステップバーをクリックして過去へ移動しても`maxReachedStep`は変更しない
- 正規の「次へ」操作を完了したときだけ`maxReachedStep`を進める
- 上流処理を変更・再生成した場合は、影響範囲に応じて`maxReachedStep`を戻す

将来的には各成果物の入力fingerprintから到達可能性を導出できるが、今回の整理では既存のfingerprintを再利用しつつ、明示的な無効化関数を正規ルートにする。

```ts
advanceWorkflow(article, nextStep)
invalidateWorkflowAfter(article, changedStep)
```

### 4.4 再生成時の無効化ルール

初期ルールを次のように固定し、テストで表現する。

| 操作                             | 操作後に直接移動できる最終ステップ | 理由                                   |
| -------------------------------- | ---------------------------------- | -------------------------------------- |
| 過去ステップを閲覧するだけ       | 変更前の`maxReachedStep`           | 成果物は変わらない                     |
| スライド検出を再実行・境界を保存 | `generate-notes`                   | OCR、文字起こし、本文は再確認が必要    |
| OCRまたは文字起こしを再実行      | `generate-notes`                   | 本文生成が古くなる可能性がある         |
| 本文生成を完了                   | `article-review`                   | 新しい本文の確認が必要                 |
| 記事タイトル・本文・要約を保存   | `export`                           | Resultは表示時に最新内容から再生成する |
| Resultを開いて生成完了           | `export`                           | 全ステップが有効                       |

補足:

- モデル選択や設定変更だけでは無効化せず、その設定で処理を実行した時点で無効化する
- 同一fingerprintで処理がスキップされた場合は無効化しない
- 処理開始時ではなく、結果の保存に成功した時点で無効化する
- 処理失敗またはキャンセル時は、最後に正常保存された到達状態を維持する
- 複数スライドの一括処理中はステップ移動を無効化し、部分結果の状態を明示する

### 4.5 ファイル操作とJSON更新の整合性を揃える

#### 作成

1. 一時ディレクトリへ動画・記事資産を生成する
2. 生成結果を検証する
3. 正式ディレクトリへrenameする
4. 新しい参照を含むプロジェクトJSONを保存する
5. JSON保存に失敗した場合は、今回作成した正式ディレクトリだけを削除する

#### 削除

1. 対象ディレクトリをプロジェクト内の`.trash/<operationId>`へrenameする
2. 対象を除いたプロジェクトJSONを保存する
3. JSON保存に失敗した場合は、対象ディレクトリを元の場所へ戻す
4. JSON保存に成功した場合は、trashを削除する
5. trash削除だけが失敗した場合は、プロジェクト自体は成功扱いとし、次回起動時に再回収する

原則:

- 必須処理では`.catch(() => undefined)`を使わない
- 失敗を無視してよい処理は、関数名を`bestEffort...`にするか呼び出し側へ理由を書く
- JSON保存前後の資産操作はrepository層へ集約し、`App.tsx`から直接呼ばない
- 同一プロジェクトへの保存はキュー化し、古い非同期結果が新しい状態を上書きしないようにする

## 11. 推奨する最初の着手単位

最初は次の3点を一つの小さな作業単位として実施する。

1. workflowの純粋関数とテストを追加する
2. `lastVisitedStep`と`maxReachedStep`を分離する
3. 変更なしの再訪と、再生成後の無効化をテストで固定する

この単位はファイル削除や大規模コンポーネント分割を伴わず、直近で変更したステップバーの仕様を先に安定させられる。その後、ストレージschemaとtransaction化を独立した作業として進める。
